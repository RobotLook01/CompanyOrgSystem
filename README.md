# 🏢 主務・兼務対応型 人事管理システム（社員所属検索＆組織図ツリー）

本プロジェクトは、実務の現場で頻繁に発生する**「1人の社員が複数の組織を兼務する（多対多の構造）」**および**「本社＞本部＞課という深い階層構造（木構造）」**を、データベース設計とバックエンド（C#）の技術で最適化して解決した、実用的な人事管理システムのプロトタイプです。

単に機能が動くだけでなく、過去のレガシーシステムメンテナンスにおける**「密結合によるデバッグの泥沼」という苦い教訓**をベースに、保守性とデータ整合性を最優先したモダンなアーキテクチャ（MVCモデル）で構築しています。

---

## 🚀 本システムの核となる「技術的アピールポイント」

### 1. 兼務に対応した「中間テーブル（多対多）」の完全分離設計
社員テーブルに所属組織IDを直接持たせる一般的な簡易設計では、複数部署の兼務に対応できません。本システムでは、社員（`employees`）と組織（`departments`）の間に**所属・兼務テーブル（`belongs`）**という中間テーブルを設置。
さらに「主務フラグ（`is_main_job`）」を設けることで、データ整合性を保ちながら、1人の社員が複数の組織に異なる役割で所属する実務要件を完全にクリアしています。

### 2. PostgreSQLの「再帰クエリ（WITH RECURSIVE）」による階層追跡の最適化
組織図のような木構造データをアプリケーション側のループ処理で何度もSQLを発行して取得すると、パフォーマンスが著しく低下します。
本システムでは、バックエンド（C#）から**PostgreSQLの再帰クエリ（WITH RECURSIVE）**を直接発行。わずか「1回」のSQLスキャンで、最上位組織から最下位組織までの全階層パス（Path）と深さ（Level）をインメモリで自動計算し、ツリー構造として視覚化する高速化・最適化を実現しています。

### 3. パスワード保護による一般／管理者の「権限分離ログイン機能」
Webシステムの基本であるセキュリティ要件として、ポータル画面（メニュー画面）を起点とした権限分離を実装。
一般ユーザーモード（閲覧用）と、管理者専用モード（機密アクセス・マスタメンテ用）をパスワード認証によってコントローラー（C#）側で厳密に制御しています。

## 🗄️ データベース設計（テーブル定義＆関係性）

Oracleデータベースで培ったリレーショナルデータ制御の知見を活かし、第三正規化および外部キー制約を厳密に設定しています。

### 組織マスタ (`departments`)
自身の中に `parent_id`（親組織ID）を持つ「隣接リストモデル」を採用し、階層の無限深化に対応。
```sql
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL,
    parent_id INT,
    FOREIGN KEY (parent_id) REFERENCES departments(department_id)
);
```

### 社員マスタ (`employees`)
```sql
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    email VARCHAR(100)
);
```

### 所属・兼務関係中間テーブル (`belongs`)
```sql
CREATE TABLE belongs (
    employee_id INT,
    department_id INT,
    is_main_job BOOLEAN DEFAULT FALSE, -- true: 主務 / false: 兼務
    PRIMARY KEY (employee_id, department_id),
    FOREIGN KEY (employee_id) REFERENCES employees(employee_id),
    FOREIGN KEY (department_id) REFERENCES departments(department_id)
);
```

## 💡 過去の苦い教沼（経験）から得た、本作の設計思想
かつて.NET Framework世代のC#によるWeb開発に携わった際、画面（コードビハインド）のロジックを安易にコピー＆ペーストして流用した結果、UI（画面制御）とデータアクセスレイヤーが密結合したスパゲッティコード化を招き、デバッグや保守対応に多大なコストを要するという極めて厳しい状況を経験いたしました。
この経験を通じて、目先の開発スピードのみを優先した運用のリスクを身をもって痛感いたしました。
以降は、保守性と拡張性を担保するための「関心の分離（アーキテクチャの選定）」や「コードの共通化・コンポーネント化」の重要性を深く認識し、設計段階における運用の先読みを徹底する原体験となっております。

この苦い思い出が、私のエンジニアとしての現在の強いこだわり（設計思想）に繋がっています。

本作品（ASP.NET Core MVC）ではその反省を100%活かし、以下の**「役割の完全分離」**を徹底しています。
1. **Model（器）**: データの構造と型定義だけに専念する
2. **Controller（ロジック）**: 画面を直接触らず、Npgsqlを駆使してSQLのデータ処理と遷移の制御だけに専念する
3. **View（画面）**: コントローラーから送られてきたデータを、Bootstrapのグリッドシステムで美しく出力することだけに専念する（`SearchScreen.cshtml` / `OrgTree.cshtml`）

### 技術的な一歩進んだ考察
今回、生SQLのパラメータバインド（`@Keyword`）を用いて強固なSQLインジェクション対策を施しましたが、これに伴い「データベースの型や列名の変更時に、DBとC#の両方をダブルメンテナンスする二重管理のコスト」が発生することを身を以て再認識いたしました。
かつて使い慣れたOracleのPL/SQL（`%TYPE`や`%ROWTYPE`による型追従自動反映）の便利さと対比し、現代のC#実務Web開発においては **Entity Framework Core（EF Core）** などのORマッパーを導入し、DBファーストでエンティティを自動生成・管理することが、型安全（コンパイルエラーでの早期検知）および開発スピードの観点から極めて重要である、というモダン開発の保守コストの真髄を学ぶことができました。

## 📱 動作確認方法（ユーザーマニュアル）
1. システムを起動すると、ポータルメニュー画面（`Index`）が表示されます。
2. **一般ユーザーとして利用する場合**: 「一般検索画面を開く」をクリック（認証不要）。青を基調とした画面で、社員名（例：「鈴木」）を入力すると、主務（営業本部）と兼務（総務部）が色鮮やかにバッジで色分けされて2行で正確に出力されます。
3. **管理者として利用する場合**: パスワード欄に **`admin123`** と入力して認証。赤を基調とした緊迫感のある「管理者専用モード」に切り替わります。
4. **組織図のツリー確認**: 管理者画面上部に現れる「🌳 組織図ツリー表示画面を開く」ボタンをクリックすると、`WITH RECURSIVE` クエリが走り、会社全体の組織構造が美しいインデント（字下げ）形式でリアルタイム表示されます。
